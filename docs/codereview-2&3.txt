        - db.py: This is the file used to estabilish a PostgreSQL database connection in order to retrieve articles from it to process and extract structured data from the same, using psycopg2.
        - embeddings.py: Main backbone for vector/similarity search in the GraphDB. When an article is pushed, its embeddings for its Title, Content (of the article), as well as the event are generated and pushed alongside the original data into the GraphDB. This allows the usage of Similarity/Vector search, which allows for more accurate and faster results for each user query. 
            PS: Embeddings are also generated for the user query, and the result is matched for maximum similarity to the 5 most similar articles containing relevant information, compared to the user query. The results are assimilated and finally structured using a final LLM call.
        - extractor.py: This is the main engine for Phase 2. It contains the system prompt defining our requirements, the GraphDB schema and the expected response format. Returns output in json format.
        - models.py: Uses Pydantic to validate the result format, obtained from the LLM. 
        - orchestrator.py: Acts as a main file to run different parts of the pipeline together. Descriptions for each functions are mentioned as follows:

Phase 3: Guidelines.
    The phase 3 deliverables were 4 APIs. It is highly advised to understand the functioning of each of the APIs here by watching the shared demo video. Since it is covered in the recording, I will not be running the demo again. I will now start with the flow chart for Phase 3, and explore the files involved in facilitating the same.
    Architecture:
        1. The user prompts any one of the API according to their need, according to the input format for each (explained thoroughly in the demo).
        2. Each of the prompt can be inferred as a question, and is forwarded to 2 functions:
            LLMCypher: To generate a cypher query (using LLM calls) to traverse the database & yield data according to the user requirements.
            EmbeddingService: Each question is given to this function as input in order to generate embeddings for the same, which enables us to use similarity search to find events/articles which correspond the most to the user's requirements.
        3. The results from both functions are obtained and are run on the GraphDB. The vector search yields the data to top 5 most similar event/article nodes to the user query, and the Cypher query generated by the LLM is run in the DB to traverse through nodes and extract the valid pieces of information related to the user query. The answers from both these modules are then combined, and then sent to a final LLM API call to structure the result and give it to the User.
        4. If the endpoint being used here is ConversationalQA API, The current answer/response will be stored in SessionStore as per history_id (last 10 turns are stored in order to not extend the context window, reducing the possibility of hallucination) in order to maintain conversation history as per chat session.
    PS: Please refer to the demo recording sent before, the working for each API is shown and explained.

    Code:
        - api.py: Contains boilerplate code for each of the 5 APIs. Auth, DailySummary, MarketThemes, Classification, CQA. Covered.
        - auth.py: Contains bearer token generation in order to provide users with access based on session. Session are interval based which can be changed as per the user requirement.
        - rag_pipeline.py: Contains the main logic for data retrieval. As explained in the architecture:
            Has 2 components that work simultaneously for each user request.
